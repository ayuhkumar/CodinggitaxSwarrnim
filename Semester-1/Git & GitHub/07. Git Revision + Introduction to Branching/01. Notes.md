## 1. Revision of Core Git Commands

These commands form the foundation of daily Git usage.

### 1.1 `git clone <repository-url>`
- Copies an existing GitHub repository to your local computer.
- Downloads all files + complete commit history.
- After cloning, you can start working immediately.

**Example:**
```bash
git clone https://github.com/username/project-name.git
```

---

### 1.2 `git status`
- Shows the current state of your repository.
- Tells you:
  - Which files are **untracked** (new files)
  - Which files are **modified** but not staged
  - Which files are **staged** and ready to commit
  - Whether the working tree is clean

**Always run `git status` before adding or committing.**

---

### 1.3 `git add`
Moves changes from the **Working Directory** to the **Staging Area**.

| Command | Meaning |
|---------|---------|
| `git add filename` | Stage one specific file |
| `git add file1 file2` | Stage multiple specific files |
| `git add .` | Stage **all** changes in the current folder |

---

### 1.4 `git commit -m "Meaningful message"`
- Creates a permanent snapshot of the staged changes in your **local repository**.
- This does **not** upload anything to GitHub.
- The message should clearly describe what was changed.

**Good examples:**
- `"Added login page"`
- `"Fixed header alignment"`
- `"Updated student form"`

**Avoid:** `update`, `changes`, `final`, `test`, `done`

---

### 1.5 `git log` and `git log --oneline`

| Command | Output |
|---------|--------|
| `git log` | Full details (commit ID, author, date, message) |
| `git log --oneline` | Short view (short commit ID + message only) |

`git log --oneline` is very useful for quick checking of history.

---

### 1.6 `git push origin main`
- Uploads your local commits to the remote repository on GitHub.
- `origin` → name of the remote
- `main` → name of the branch

## 2. Two Methods to Push Code to GitHub

### Method 1: When you already cloned the repository

This is the most common method after `git clone`.

```bash
# 1. Make changes in files
# 2. Check status
git status

# 3. Stage the changes
git add .

# 4. Commit locally
git commit -m "Added new feature"

# 5. Push to GitHub
git push origin main
```

---

### Method 2: Starting from a local project (New Repository)

Use this method when you create a project on your computer first and then want to put it on GitHub.

#### Complete Steps:

```bash
# Step 1: Initialize Git in the folder
git init

# Step 2: Stage all files
git add .

# Step 3: Check status
git status

# Step 4: Create first commit
git commit -m "Initial commit"

# Step 5: View commit history
git log
git log --oneline

# Step 6: Connect local repo to GitHub
git remote add origin https://github.com/username/repo-name.git

# Step 7: Rename branch to main (important)
git branch -M main

# Step 8: Push code and set upstream
git push -u origin main
```

---

### Explanation of New Commands in Method 2

| Command | Purpose |
|---------|---------|
| `git init` | Turns the current folder into a Git repository |
| `git remote add origin <url>` | Links your local repository to a GitHub repository |
| `git branch -M main` | Renames the current branch to `main` |
| `git push -u origin main` | Pushes the code and sets the upstream tracking relationship |

> **Note:**  
> After using `-u` once, you can simply use `git push` next time.

## 3. Introduction to Git Branching

### 3.1 What is a Branch?

A **branch** is an independent line of development.

It allows you to work on new features, bug fixes, or experiments **without affecting** the main codebase.

- The default branch is usually called **`main`** (earlier it was called `master`).
- When you create a new branch, you get a separate workspace.

---

### 3.2 Why Do We Need Branching?

#### Problems without Branching:
- Everyone works directly on the `main` branch
- One person makes a mistake → entire project can break
- Difficult to work on multiple features simultaneously
- No safe way to experiment with new ideas
- Hard to keep the main code stable and clean

#### Benefits of Using Branches:
- `main` branch remains stable and production-ready
- Each feature can be developed in isolation
- Multiple developers can work in parallel
- Easy to experiment without fear
- You merge the feature into `main` only when it is complete and tested

---

### 3.3 Simple Analogy

Think of it like roads:

- **`main` branch** = Main road (should always be clean and usable)
- **Feature branch** = Side road where you can freely experiment and build
- **Merge** = Joining the side road back to the main road when the work is ready

---

## 4. Basic Workflow Recap

```text
Working Directory
       ↓  git add
Staging Area
       ↓  git commit
Local Repository
       ↓  git push
Remote Repository (GitHub)
```

---

## 5. Key Points to Remember

1. Always check `git status` before adding or committing.
2. Write clear and meaningful commit messages.
3. `git commit` saves work **locally**. `git push` uploads it to **GitHub**.
4. Use Method 2 (`git init` + `remote add`) when starting a new project locally.
5. `git branch -M main` ensures your branch is named `main`.
6. Branching helps teams work safely and in parallel.
7. Never be afraid to create branches — they are cheap and safe.

> There are **two common ways** to push code to GitHub:
