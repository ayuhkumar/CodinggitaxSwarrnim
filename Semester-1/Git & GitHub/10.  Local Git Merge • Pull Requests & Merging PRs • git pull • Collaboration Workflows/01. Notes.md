# Local Git Merge • Pull Requests & Merging PRs • git pull • Collaboration Workflows

## Learning Goals

- Perform a local merge using `git merge`.
- Create a Pull Request, review it, and merge it on GitHub (hands-on).
- Understand the difference between local merge and PR merge workflows.
- Use `git pull` to bring remote changes into your local branch.
- Know when to use local merge vs Pull Request merge.

## 1. Local Git Merge

A **local merge** combines changes from one branch into another **on your computer**. It does not involve GitHub until you push.

### Basic Local Merge Commands

```bash
# Make sure you are on the target branch (usually main)
git checkout main

# Get latest remote changes first (recommended)
git pull origin main

# Merge the feature branch into main
git merge feature-branch

# After successful merge, push the updated main
git push origin main
```

### What Happens During a Local Merge?

| Type          | When it happens                        | Result                              |
|---------------|----------------------------------------|-------------------------------------|
| Fast-forward  | Target branch has no new commits       | Branch pointer simply moves forward |
| 3-way merge   | Both branches have new commits         | Creates a merge commit              |
| Conflict      | Same lines changed in both branches    | Git stops and asks you to resolve   |

**Fast-forward example:** If `main` has not moved and your feature branch is ahead, Git just moves the `main` pointer forward. No extra merge commit is created.

## 2. Pull Request (PR) and Merging a PR

A **Pull Request** is a request on GitHub to merge one branch into another. It allows review, discussion, and controlled merging.

### Complete PR Workflow (Hands-on)

1. Create feature branch and make changes  
2. Push the branch to GitHub  
3. Open a Pull Request (GitHub UI or from the push message link)  
4. Review / request changes (comments, approvals)  
5. Revise if needed → commit + push to the same branch (PR updates automatically)  
6. Merge the PR on GitHub (Merge pull request button)  
7. Delete the feature branch (optional but recommended after merge)  
8. Update your local main with `git checkout main && git pull`

### Commands used in the PR workflow

```bash
# Create and switch to feature branch
git checkout -b feature-login

# Make changes, then stage and commit
git add .
git commit -m "Add login page"

# Push feature branch to GitHub
git push -u origin feature-login

# After PR is merged on GitHub, update local main
git checkout main
git pull origin main
```

### Merging Options on GitHub

| Option                | What it does                          | When to use                        |
|-----------------------|---------------------------------------|------------------------------------|
| Create a merge commit | Keeps full history + merge commit     | Default; clear history of merges   |
| Squash and merge      | Combines all PR commits into one      | Clean history; many small commits  |
| Rebase and merge      | Replays commits on top of target      | Linear history (advanced)          |

## 3. Local Merge vs PR Merge – Workflow Comparison

| Aspect              | Local Merge (`git merge`)              | PR Merge (on GitHub)                     |
|---------------------|----------------------------------------|------------------------------------------|
| Where it happens    | On your computer                       | On GitHub server                         |
| Review process      | None (unless you ask someone)          | Built-in review, comments, approvals     |
| Visibility          | Only you (until you push)              | Team can see and discuss                 |
| History             | Merge commit appears after push        | Merge recorded on GitHub                 |
| Best for            | Personal projects, quick local work    | Team collaboration, code review          |
| Typical action      | `git merge feature`                    | Click “Merge pull request”               |

**Key idea:** Local merge is private and fast. PR merge is public, reviewable, and safer for teams.

## 4. git pull

`git pull` brings remote changes into your current local branch. It is a combination of two steps: `git fetch` + `git merge`.

### Basic usage

```bash
# Pull latest changes from origin into current branch
git pull

# Explicit form (recommended when learning)
git pull origin main

# After switching to main, always pull before starting new work
git checkout main
git pull origin main
```

### git pull vs git fetch

| Command       | What it does                                      | Changes your files? |
|---------------|---------------------------------------------------|---------------------|
| `git fetch`   | Downloads new commits from remote only            | No                  |
| `git pull`    | Downloads + merges into current branch            | Yes                 |

**Safe habit:** Many developers prefer `git fetch` first, then look with `git log` / `git diff`, and only then merge. `git pull` is convenient when you trust the remote changes.

## 5. Complete Workflows (Summary)

### A. Local Merge Workflow

```bash
1. git checkout main
2. git pull origin main          # stay up to date
3. git merge feature-branch
4. (resolve conflicts if any)
5. git push origin main
```

### B. Pull Request Merge Workflow

```bash
1. git checkout -b feature-xyz
2. (make changes) → git add . → git commit -m "..."
3. git push -u origin feature-xyz
4. Open Pull Request on GitHub
5. Review / revise / approve
6. Merge Pull Request on GitHub
7. git checkout main
8. git pull origin main          # bring merged work locally
```

## 6. Important Reminders

- Always pull (or fetch) before starting new work on `main`.
- Never force-push to `main` or any shared branch.
- After a PR is merged on GitHub, run `git pull` on your local `main`.
- Delete feature branches after they are merged to keep the repository clean.
- If a conflict appears during merge or pull, resolve it, then `git add` + `git commit`.

## 7. Practice Task

1. Create a new feature branch and make a small change (edit a file or add a new file).
2. Push the branch and open a Pull Request on GitHub.
3. Merge the Pull Request using the GitHub interface.
4. Switch to local `main` and run `git pull`. Confirm the change is now on `main`.
5. Create another feature branch, make a different change, and this time merge it **locally** with `git merge`, then push `main`.
6. Compare the two approaches and note the difference in history (`git log --oneline`).

## Quick Revision Cheat Sheet

| Command / Action                          | Purpose                                      |
|-------------------------------------------|----------------------------------------------|
| `git checkout -b feature-name`            | Create and switch to a new branch            |
| `git merge feature-name`                  | Merge feature branch into current branch     |
| `git push -u origin feature-name`         | Push new branch and set upstream             |
| Open Pull Request on GitHub               | Request to merge branch with review          |
| Merge pull request (GitHub button)        | Merge after review on GitHub                 |
| `git pull` / `git pull origin main`       | Download + merge remote changes              |
| `git fetch`                               | Download remote changes without merging      |
| `git log --oneline`                       | View compact commit history                  |
| `git status`                              | Check current state before merge/pull        |

## Key Takeaway

- **Local merge** = combine branches on your machine  
- **PR merge** = combine branches on GitHub with review  
- **`git pull`** = fetch + merge remote changes into your current branch  
- Always keep local `main` updated with `git pull` after a PR is merged
