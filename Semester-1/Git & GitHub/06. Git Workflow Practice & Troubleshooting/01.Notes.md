

# Git Workflow and Troubleshooting
---

## Learning Goals

By the end of this session you will be able to:

- Understand the difference between Git configuration and GitHub authentication.
- Use `git status` to inspect the state of your repository.
- Stage changes with `git add`.
- Create commits with `git commit`.
- View commit history with `git log`.
- Connect a local repository to GitHub using a remote.
- Push commits to GitHub.
- Understand and troubleshoot 403 and authentication/authorization errors.

## 1. Git Configuration vs GitHub Authentication

These two concepts solve **completely different problems**. Confusing them is one of the most common sources of errors.

| Git Configuration | GitHub Authentication | Simple Question |
|---|---|---|
| Identifies the author of commits | Verifies identity when accessing GitHub | Who created this commit? |
| Configured with `git config` | Handled through GitHub sign-in / credentials | Who is accessing GitHub? |
| Does **not** grant push permission | Controls access to the remote repository | Am I allowed to access this repository? |

### Configuration Commands

Set your name and email (these appear in every commit you create):

```bash
git config --global user.name "Your Name"
git config --global user.email "your@email.com"
```

Check the values currently stored:

```bash
git config --global user.name
git config --global user.email
git config --list
```

**Important:** Changing Git configuration does **not** log you into GitHub and does **not** give you permission to push to any repository.

## 2. GitHub Authentication

Authentication proves which GitHub account is trying to access a remote repository. When you use HTTPS, Git for Windows typically relies on Git Credential Manager and may open a browser window for you to sign in.

- You may be asked to authenticate the first time you push (or after credentials expire).
- The authenticated GitHub account must have write (push) permission on the target repository.
- Having the correct Git name and email does **not** automatically grant GitHub permission.
- **Never share passwords, personal access tokens, or any credentials.**

| Authentication | Authorization |
|---|---|
| Who are you? | What are you allowed to do? |
| Verifies the GitHub account identity | Checks repository permissions for that account |
| Example: sign-in / credential verification | Example: permission to push to a specific repo |

## 3. git status

`git status` is the command you should run most often. It shows the current state of your working directory and staging area.

```bash
git status
```

| Message | Meaning |
|---|---|
| Untracked files | New files that Git is not tracking yet |
| Changes not staged for commit | Tracked files were modified but have not been staged |
| Changes to be committed | Changes are staged and ready to be committed |
| Working tree clean | No uncommitted changes exist |

---

## 4. git add

`git add` moves changes from the working directory into the staging area. Only staged changes will be included in the next commit.

**Stage one specific file:**
```bash
git add index.html
```

**Stage all changes** in the current directory and subdirectories:
```bash
git add .
```

**Flow:**
```
Working Directory  →  git add  →  Staging Area
```

---

## 5. git commit

A commit permanently records the staged changes in your **local** Git repository. It does **not** upload anything to GitHub.

```bash
git commit -m "Added initial files"
```

**Good commit messages** describe the change clearly. Examples:
- Added login page
- Updated navigation bar
- Fixed button alignment
- Added student profile

**Avoid vague messages** such as “update”, “changes”, “done”, or “test”.

| Command | Movement |
|---|---|
| `git add` | Working Directory → Staging Area |
| `git commit` | Staging Area → Local Repository |
| `git push` | Local Repository → Remote / GitHub |

---

## 6. git log

`git log` displays the commit history of the current branch.

```bash
git log
git log --oneline
```

The `--oneline` flag produces a compact view that makes it easy to scan commit IDs and messages.

### Example Workflow – Two Commits

```bash
git status
git add .
git commit -m "Added initial files"
```

… make another change …

```bash
git status
git add .
git commit -m "Updated project files"
git log --oneline
```

---

## 7. Remote Repository

A remote is a reference (usually a URL) to another Git repository. In most student projects the remote points to a GitHub repository.

**View existing remotes:**
```bash
git remote -v
```

`origin` is the conventional name given to the primary remote.

**Add a remote** if one does not yet exist:
```bash
git remote add origin <repository-url>
```

Always verify after adding:
```bash
git remote -v
```

---

## 8. git push

`git push` uploads your local commits to a remote repository (GitHub).

**First push** (sets the upstream tracking relationship):
```bash
git push -u origin main
```

| Part | Meaning |
|---|---|
| `git push` | Send local commits to the remote |
| `-u` | Set upstream relationship so future pushes are simpler |
| `origin` | Name of the remote |
| `main` | Name of the branch being pushed |

After the upstream is configured, later pushes can usually be shortened to:
```bash
git push
```

---

## 9. Complete Basic Workflow

The everyday cycle you will repeat for almost every change:

1. Modify or create files in your project
2. `git status` – inspect what changed
3. `git add .` – stage all changes
4. `git commit -m "Meaningful message"` – save locally
5. `git push origin main` – upload to GitHub
6. Verify the new commit and files appear on the GitHub website

## 10. 403 Permission Denied

A 403 error means GitHub understood your request but refused to perform it because of insufficient permission.

**Typical error message:**
```
remote: Permission to username/repository.git denied to another-username.
fatal: unable to access ... 403
```

### Possible Reasons
- The authenticated GitHub account does not have permission to push.
- The remote URL points to someone else’s repository.
- You only have read (clone/pull) access, not write access.
- The wrong GitHub account is stored by the credential manager.

### What to Check
```bash
git remote -v
git config --global user.name
git config --global user.email
```

Also open a browser, confirm which GitHub account is currently signed in, and verify that account has write access to the target repository.

---

## 11. Authentication Failed / Authorization Failed

These two failures look similar but have different root causes.

| Concept | Meaning | Example |
|---|---|---|
| Authentication | Who are you? | GitHub sign-in / credential verification |
| Authorization | What can you do? | Can this account push to this repository? |

- **Authentication failure** → Git could not successfully verify the credentials or session.
- **Authorization failure** → The account was recognized but is not allowed to perform the requested action.

## 12. Troubleshooting Checklist

When something goes wrong, work through this list systematically:

1. Read the complete error message carefully.
2. Run `git status`.
3. Check the current branch with `git branch`.
4. Check the remote with `git remote -v`.
5. Inspect configuration with `git config --list`.
6. Confirm the correct GitHub account is authenticated.
7. Confirm that account has permission to push to the repository.
8. Try the original command again after fixing the issue.
9. **Never share passwords or tokens.**
